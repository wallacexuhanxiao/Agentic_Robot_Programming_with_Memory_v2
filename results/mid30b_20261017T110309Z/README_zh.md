# 中间层 primitive + Qwen3-30B：与 task 级对比

## 运行信息

- **作业**：Hopper interactive 队列，1 张 GPU。
  - `672359`：门控和前 7–9 个任务。
  - `672468`：在同一输出目录用 `--resume` 补跑剩余任务。
  - `672354`：首次提交，因 PBS 脚本 bug 只跑完门控就退出，见“运行问题”。
- **代码**：提交 `772fe1b`（672359）和 `1536170`（672468，只增加了续跑和崩溃诊断）。
- **API 级别**：`SMA_API_LEVEL=mid`，接口见 `docs/MID_LEVEL_API_zh.md`。
- **模型**：Qwen3-30B-A3B-Instruct-2507（bf16，vLLM）承担全部角色，和 task 级那次（作业 `672093`）是同一个模型。
- **任务序列**：两次都是 `session` 的 10 个任务：1 个教学、3 个明确指令、6 个新布局上的模糊指令。
- **信息边界**：感知只用俯视 RGB-D 颜色分割，仿真真实状态只用于下表的 GT 评分。

## 脚本门控（不调用模型）

结果在 `mid_gate/`、`mid_gate.log`。

- 几何抓取候选：积木、书、杯子、清空被占容器 4 个任务，GT 4/4。
- Contact-GraspNet 候选：每个物体给出 1–18 个抓取，但几乎都不是从上往下接近（与竖直夹角 ≤30° 的只有 0–2 个），唯一一次可执行的也没抓住。

所以下面的实验里，**几乎只有几何候选在起作用**：91 次 `grasp_candidates` 调用里，只有 1 次出现了 GraspNet 候选（`user/tidy_1003`，该任务失败）。GraspNet 的采样有随机性，重放时它偶尔会多给出一个从上往下的候选，见 `../replaymid_*/` 的说明。

## 主要结果（单次运行，每个条件 10 个任务）

| 指标 | 无记忆 | 只开技能记忆 | 只开用户记忆 | 两种记忆 |
|---|---|---|---|---|
| **mid 级**：任务成功（GT） | 5/10 | 5/10 | 8/10 | 8/10 |
| task 级：任务成功（GT） | 4/10 | 5/10 | 9/10 | 9/10 |
| mid 级：子目标相机验证通过 | 13/16 | 13/16 | 13/18 | 14/18 |
| task 级：子目标相机验证通过 | 11/17 | 11/16 | 15/18 | 15/18 |
| mid 级：执行尝试 / 失败执行 | 22 / 9 | 22 / 9 | 28 / 15 | 28 / 14 |
| task 级：执行尝试 / 失败执行 | 31 / 20 | 28 / 17 | 33 / 18 | 26 / 11 |
| mid 级：调用已学技能次数 | 0 | 6 | 0 | 10 |
| mid 级：LLM 调用 / 生成 token | 60 / 9441 | 57 / 10577 | 80 / 10567 | 71 / 11905 |
| task 级：LLM 调用 / 生成 token | 87 / 10479 | 66 / 8850 | 95 / 9917 | 70 / 7205 |

参照：同一模型在 pose 级（`move_to` 加夹爪）是 0/26，在 ASPIRE 级 campaign 里全部 0 成功。

## 结论

1. **抽象层次降到中间层，30B 仍然可用。** 有用户记忆时 8/10，task 级是 9/10，差一个任务，在单次运行的波动范围内。现在由模型决定的东西比 task 级多：选哪个抓取候选、放在容器的哪个位置和朝向、什么时候松手、失败后怎么恢复。
2. **用户记忆仍然是模糊指令成败的关键**：无记忆 5/10，有记忆 8/10。无记忆时精炼器只能猜目标（`assumption`），例如把杯子放到橙色托盘、把书放进紫色箱。
3. **技能记忆在这一层的作用不明显。**
   - 从成功执行里提取出按物体分的技能，并在受控新布局上验证过；之后被直接复用 6 次（只开技能记忆）和 10 次（两种记忆），例如 `tidy_1004`、`tidy_1005` 全程只靠调用技能完成，没有写新代码。
   - 但对比“两种记忆”和“只开用户记忆”：失败执行 14 对 15，LLM 调用 71 对 80，token 反而更多。task 级那次失败执行是 11 对 18，差距明显得多。这一层的技能记忆还没有带来稳定的效率提升。
4. **适用性检查 16 次里对了 13 次。**
   - 2 次错误判定发生在 `tidy_1003`：技能是模型自己声明“目标容器被占也能用”（`requires_zone_free: false`）。实际它会先抓起物体，发现容器满了就直接返回，物体还拿在手里，录像最后一帧可以看到。
   - 检查器相信了这个自我声明。说明适用条件需要用验证结果来约束，而不能只靠模型自报。

## 失败原因

| 类型 | 出现位置 | 说明 |
|---|---|---|
| 书在带围墙的玩具箱里，抓不出来 | 4 个条件的 `tidy_1003` | 书的抓取下降被箱壁挡住，报 `motion_blocked`。task 级同一任务也失败，属于已知的抓取或场景局限 |
| 模型用错返回值或沙箱限制 | 多处 | 在错的字典上取键（`'occupants'`、`'table_z'`、`'long_axis_yaw'`）；用了沙箱没有的 `next`；用了被禁止的 `lambda` |
| **primitive 设计缺陷（我的问题）** | `both/tidy_1001` | 模型自己重组了抓取候选字典，去掉了 `object_footprint` 等字段，`grasp()` 抓起后不知道手里物体的外形，于是 `free_spots` 报 `footprint_unknown`，书一直拿在手里。应该改成由 `grasp()` 自己从感知里记录外形，不依赖调用方传入 |
| 感知误检出“幻影物体” | `none/tidy_1002`、`skill/tidy_1002` | 托盘边缘被颜色分割识别成一本 `yellow_book`（高 8 mm、宽 0，真实场景里没有）。它被当成目标，浪费了尝试次数。task 级也出现过同样的误检 |
| 规划器把目标改错 | `skill/place_3` | 指令目标是紫色箱，规划器给出了橙色托盘；`parse_plan` 只检查名字存在，没有核对目标是否一致 |

## 运行问题（如实记录）

- **首次提交 `672354`**：门控通过后，因 `SMA_VLLM_EXTRA` 未设置，在 `set -u` 下退出。已修复。
- **作业 `672359`**：模拟进程在 4 个条件里都在启动后约 14–17 分钟以 `Aborted (core dumped)` 退出，位置在第 7–9 个任务，没有 Python 异常。
  - 这个进程整体比正常慢 5–10 倍，单个任务要 30–390 秒；续跑作业在另一个节点上，同类任务只要 10–30 秒。
  - 原因未定位，怀疑是该节点上的渲染或底层库问题。续跑加了 `-X faulthandler`，但这次没有再崩溃，所以没有拿到调用栈。
- **续跑**：`--resume` 保留已完成任务、磁盘上的技能记忆和用户记忆，只重跑崩溃时未完成的任务。崩溃时的半成品目录被改名为 `<task>.crashed_*`（如有）。续跑的任务在 `summary.json` 中标为 `after_resume: true`。
  - 各条件续跑的任务：两种记忆、只开用户记忆为 `tidy_1003–1005`；无记忆为 `tidy_1004–1005`；只开技能记忆为 `tidy_1002–1005`。
- 运行速度只影响墙钟时间，不影响模型输入和物理结果：仿真按控制步推进，模型看不到时间。
